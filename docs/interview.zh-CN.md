# 求职与面试讲解

## 简历项目名称与描述

**Research Workflow Skills｜可审计的 AI 研究工作流**

将研究任务拆为宿主 Agent、五个 Skill 与确定性文件引擎，使用结构化计划连接语义复核和代码执行；实现输入与计划哈希绑定、完整复核覆盖、引用片段和数值检查，以及带脱敏凭证的 Excel/PPT 交付。通过合成正反例验证失败路径，并以微软 Open XML SDK 校验输出。

这段描述可直接使用；测试数量以仓库当期验收记录为准。不要补写未经测量的提效比例、业务收入、用户规模或生产稳定性。

## 30 秒介绍

我关注的是：模型生成了一个看起来合理的结果，工程系统如何决定它是否可以交付？这个项目把推理放在宿主 Agent，把输入版本、复核覆盖和文件完整性放进代码。五个技能共享导出门禁；例如漏审一行、修改已复核计划或伪造来源片段，都会阻止最终输出。公开演示全部使用合成数据，可以一条命令复现。

## 两分钟演示顺序

1. 先运行 README 中的 demo 命令，展示五份文件与 `summary.json`。
2. 打开贴数图表及输入 `metrics.xlsx`：100、140 对应两个明确单元格，计划记录目标 shape ID。
3. 展示 QC 原始页与新增复核页，解释 `uncertain` 为什么没有被改成 `clean`。
4. 打开伪造引用或缺失复核测试，说明失败后没有最终文件和成功凭证。
5. 展示 CI 与微软校验记录，最后解释边界：这些检查约束代码和文件，不证明模型已经理解所有业务含义。

## 常见追问

| 问题 | 可核验的回答 |
|---|---|
| 为什么采用 Skill？ | 当前任务以研究与文件交付为主，可以复用宿主能力，把开发重点放在可测试的文件边界；独立运行时需要另外实现状态、预算与调度。 |
| 这是两个模型互相验真吗？ | 不是。本版是宿主语义复核与确定性代码校验两个层次；演示中的复核结果还是预写的合成夹具。 |
| 哈希能证明结果真实吗？ | 哈希证明复核对象和执行对象一致。真实性仍依赖来源和语义复核。 |
| 你怎样防止错误知识越学越多？ | SkillOpt 接入先评测候选、检查验证集逐例不退化、观察独立测试，再单独采用；公开版只验证了 mock 接入，不宣称模型效果提升。 |
| 企业化还缺什么？ | 用户与权限、任务持久化、并发与预算、可恢复执行，以及真实业务样本上的误杀/漏检评估。 |
| AI 在项目中做了什么？ | 实现使用了 AI 辅助。应能解释设计、定位问题、维护代码和复现测试；不要声称逐行手写或无工具辅助。 |

## 岗位侧重点

- **AI 应用 / Agent 工程**：讲清宿主与引擎边界、结构化计划、失败路径和评测。
- **数据 / 自动化工程**：展示单元格到图表的映射、输入保护、审计凭证和 Office 校验。
- **AI 产品 / 解决方案**：解释为什么去掉平台外壳、哪些能力适合 Skill、哪些需要独立 Agent，以及如何定义交付完成。

这是公开作品集的讲解建议，不替代个人真实经历。与面试官讨论时应区分本人负责的决策、AI 辅助实现和依赖库提供的能力。
