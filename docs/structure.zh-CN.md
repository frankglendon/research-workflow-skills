# 研究 Agent 与 Skill 的结构方案

建议采用 **一个宿主研究 Agent + 六个专业 Skill + 共用校验引擎**。代码包有七个 Skill 目录：一个总入口、六个专业能力；这不代表七个独立 Agent。

| 模块 | 负责什么 | 主要交付 |
|---|---|---|
| 研究总入口 | 理解任务、选择流程、维护交接与版本 | 研究计划、阶段状态、交付清单 |
| 案头研究 | 问题拆解、取证、核验、形成故事线 | 来源与断言台账、缺口表、研究报告 |
| 问卷设计 | 商业问题转指标与题目、抽样与编程设计 | 问卷、分析映射、编程说明、路径用例 |
| 码表设计 | 变量与答案编码、开放题分类定义 | 变量字典、Datamap、开放题编码框架 |
| 数据 QC | 答案质量与逻辑复核 | 保留原始数据的质检结果 |
| 报告贴数 | 确认数据来源与图表映射 | 可编辑报告图表 |
| 报告翻译 | 翻译与数字、结构保留 | 复核后的译稿 |

这些模块按任务组合，不必每次全跑。例如纯案头任务直接走取证与报告；问卷改版只运行问卷、码表及相关复核。

总入口新增 [研究项目分类](../skills/research-workflow/references/project-types.md)：体验忠诚、品牌健康、品牌定位、人群细分、使用需求、产品创新、价格价值、购买渠道、营销传播、市场增长。按主辅商业目标选择流程，方法、周期与国家范围另记。10 类项目共用六个专业 Skill；规划人群或价格研究不代表已实现聚类、价格弹性等统计引擎。

## 为什么这样拆

问卷回答“问什么、向谁问、如何出示”，码表回答“答案怎么存、怎么解释、怎么分析”。码表还会独立服务历史数据或其他问卷，因此单独做 Skill 更合适；两者必须依赖同一份问卷规范与版本，避免各写各的。

当前用一个宿主统筹，能复用现有搜索、文件和推理能力，维护成本较低。代价是工具能力、上下文容量和任务持续时间受宿主限制。

独立 Agent 需要自己的模型与工具循环、任务状态、重试、预算和权限控制。优点是可持续运行、隔离职责、并行调度；代价是成本更高，版本交接和故障处理更复杂。只有当案头研究或编程复核出现可测量的独立需求时，再将相应 Skill 外包一层 Agent 运行时。

## 这次实际实现的范围

- 问卷 v2：10 种结构化题型、目标映射、显式向前跳转与出示条件、合成分支覆盖检查。
- 码表：单选标签、多选二分变量、矩阵/排序展开、指定程序变量名、长表 Datamap、开放题编码定义。
- 版本门禁：问卷改动使复核和码表失效；码表修改需重新复核；Office 文件通过微软校验后才发布到新路径。
- Datamap 读取：三类布局的表头与列清单识别，保留来源哈希；不是任意码表的自动转换器。
- 总入口和案头研究：完善宿主执行流程、阶段交接、取证循环与停止条件。

**尚未实现**：独立无人值守 Deep Research 运行时、自动批量开放题编码、复杂回圈/动态题干的调查平台编程、完整测程平台。案头展示命令仍从已有证据台账生成页面；真实检索、分析与完整故事线由宿主执行。没有把这些未完成能力算入演示成绩。

## 建议的落地顺序

先在当前宿主使用六个 Skill 跑一个完整项目，验证问题—问卷—码表—数据—报告的交接。保留失败案例并转成获准的合成评测；SkillOpt 只提出候选，经过评测后再采用。

随后判断两个方向：案头研究是否需要长时间自动补证；问卷与码表是否需要接入实际调查程序。这两类真实需求决定是否增加独立 Agent，而不是先堆多个角色名称。
